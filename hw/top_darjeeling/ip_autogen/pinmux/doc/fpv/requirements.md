# Pinmux FPV requirements

What the Darjeeling pinmux must do, one testable statement per row, in one group per feature.
Each row cites the specification text it comes from, names the testplan checks that decide it and says why those checks prove it.
A row marked *RTL* states a rule that no specification gives: it follows the design's present behaviour.
A row that says its outcome is open waits on a specification question, and no check decides it until the question is answered.
The rows are rendered from [`pinmux_fpv_requirements.hjson`](../../data/pinmux_fpv_requirements.hjson), which also holds the state of each.
How the requirements, testpoints and checks fit together: [Pinmux FPV document](README.md).

This page is rendered for this top from the pinmux template by `make -C hw top`.
The plan was written and reviewed for Earl Grey only: no requirement has been read against this top's specification, so every requirement is open.

## Terms

| Term | Meaning |
|---|---|
| `n` | MIO peripheral input (0 to 3) |
| `k` | MIO peripheral output (0 to 4) |
| `p` | MIO pad (0 to 11) |
| `d` | DIO pad (0 to 72) |
| Watched signal | The pad input that `MIODIO` and `PADSEL` pick |
| Forwarded value | The watched signal sampled each `clk_aon_i` cycle, through the filter when `FILTER` is 1 |

## Pad attributes

Conditions: Every row holds in every cycle, asleep or awake, except on a JTAG pad while a TAP owns it.
"Written" means a write the register block accepts, its lock open (Register locks); "reads back" means what a read of the register returns.
A pad type "keeps" an attribute bit when its pads implement that bit ([Pad Attributes](../programmers_guide.md#pad-attributes)); which bits a type keeps is fixed, the same on every pad of the type and for good.
A one-bit field is kept when its bit is; each bit of `slew_rate` and `drive_strength` is kept or not on its own, as "certain pads may only support two drive-strength bits, instead of four" ([Pad Attributes](../programmers_guide.md#pad-attributes)).
Every pad keeps `invert` ([Generic Pad Wrapper](../theory_of_operation.md#generic-pad-wrapper)).

## Register block and bus

Security-relevant: a security claim depends on these requirements.

Conditions: A "failed request" is a request whose command integrity code does not match, or a write whose data integrity code does not match ([Usage of User Bits](../../../../../ip/tlul/README.md#usage-of-user-bits): the data code covers "the write data").
A read whose only mismatch is in its data code is not a failed request, and no row checks its response or its alert.
The "in-band reset" is the alert handler's re-initialization, during which it puts a signal integrity error on its ping and acknowledge pairs on purpose ([Employed Solution](../../../../../top_earlgrey/ip_autogen/alert_handler/doc/theory_of_operation.md#employed-solution)).
The sender's answer to it, a signal integrity error on `alert_tx_o` and then a return to idle ([Employed Solution](../../../../../top_earlgrey/ip_autogen/alert_handler/doc/theory_of_operation.md#employed-solution)), has no row: the sender is the shared primitive `prim_alert_sender` (`rtl/pinmux.sv`:143-147), whose own upstream FPV drives the in-band reset and checks the return to idle (`hw/ip/prim/fpv/tb/prim_alert_rxtx_*`, `InBandInitFromReceiverToSender_A`).
The alert rows read `alert_tx_o`, with an alert handler.
An "illegal combination of address, size and mask" is a request whose address, size and mask do not correspond as TileLink requires (TileLink 1.9.3 p. 49-51: "a_size, a_address and a_mask are required to correspond with one another"): an address not aligned to its size (p. 51: "a_address must be aligned to a_size"), a size above 2, a mask bit set on a byte lane outside the access, or a `PutFullData` whose mask leaves a lane of the access 0.
[Explicit Error Cases](../../../../../ip/tlul/README.md#explicit-error-cases) lists the last three "for example"; the unaligned address is verification's reading.

## Wakeup detectors

Conditions:

* `w` is a detector (0 to 7); a cycle is a `clk_aon_i` cycle (watched signal, forwarded value: terms).
* Register values are those the AON logic holds once a write has crossed.
* The rows hold with scan mode not True.
* They hold with the mode unchanged while enabled; the other fields may change while enabled.
* They hold whatever `sleep_en_i` does.
* They hold whatever `clk_i` does, stopped included: in sleep "only the wakeup detector logic will be actively clocked" ([Retention and Wakeup Features](../theory_of_operation.md#retention-and-wakeup-features)).
* They are checked from the filter's fourth sample after `rst_aon_ni`.
* The timed rows (`REQ_WKUP_09a` to `REQ_WKUP_10b`) hold for `CNT_TH` 1 and above: no spec says what a timed detector does with 0, the reset value.

Testpoints: `wakeup` (V2, priority 1), `wakeup_cause` (V2, priority 2), `wakeup_sync` (V2, priority 2).
